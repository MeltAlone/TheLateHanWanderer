# 世界机器实施计划

> 状态：执行中<br>
> 最近更新：2026-07-24<br>
> 当前实现：`0.6.1-spike`

## 1. 这份文档负责什么

本文件是项目从设计与历史资料走向可玩动态世界的总执行入口，回答三个问题：已经完成了什么、当前真实能力到哪里、接下来按什么顺序实现和验收。

玩法原则以[世界模拟总设计](design/overview.md)为准，命令与行为以[命令行 MVP 规格](design/mvp-spec.md)为准，领域边界以[世界模型](architecture/world-model.md)为准，具体技术选择由[架构决策记录](decisions/README.md)约束。本计划只安排工作，不覆盖这些上位契约。

## 2. 最终目标

建立一台玩家可以从个人视角进入的汉末世界机器：时间和空间持续约束所有人；人物依据有限认知、身份、资源和动机形成计划；行动需要真实耗时并可能失败或中断；消息、承诺和物质变化留下可查询因果；相同场景、随机种子和命令必须确定性重放。

第一阶段完成标志不是“拥有很多命令”或“做出图形界面”，而是[雒阳四日验收规格](../tests/specs/189-luoyang-crisis.md)中的核心路径能够由通用规则运行，并满足[世界规模预算](../tests/performance/world-scale-budgets.md)的阶段门槛。

## 3. 已经完成

### 3.1 设计、研究与数据基础

- 已建立时间、空间、人物、组织、认知、行动、事件和因果的总体设计纪律。
- 已建立史料来源、历史主张、置信度、争议和有界推断的研究流程。
- 已定义 189 年雒阳危机四日切片，以及人物、地点、路线、物品、信念、承诺和计划场景夹具。
- 已定义 CLI MVP 精确命令、行为验收用例、世界不变量和 L0-L3 规模预算。
- 场景 JSON 已具备跨文件 ID/引用、来源覆盖和规范化内容哈希校验。

### 3.2 C#/.NET 纵向切片

- 已建立 `Core <- Scenarios/Persistence <- CLI` 的单向依赖边界；核心不依赖 JSON、数据库或界面框架。
- 已实现查询、确定性最短路径移动、交付、陈述、等待、承诺完成和不可变因果事件。
- 已实现版本化快照 DTO、原子文件替换、保存/加载后的确定性续跑。
- 已实现完整送信路径：54 分钟、11 个事件、两项承诺关闭；回报现在显式形成消息送达与接收者信念。
- 已固定 .NET 10 SDK、Release 零警告、格式检查、依赖漏洞扫描和自动测试工作流。

### 3.3 世界机器 `0.2` 基础

- 已实现持久未来事件队列，稳定排序键为 `(due_minute, phase, stable_subject_id, sequence)`。
- 已实现同一分钟完整批次结算，不依赖集合插入顺序，也不给玩家隐藏优先权。
- 已让 `wait` 按事件边界推进；四小时等待可在第 95 分钟精确中断，剩余 145 分钟不发生。
- 已实现 `xoshiro256ss.v1` 和 `sha256-le.v1` 领域隔离随机流，固定参考向量和跨流独立性测试。
- 快照 schema `0.2` 已保存未来事件、序号游标、根种子、随机流状态、抽取次数和回放修改标记。
- 已加入只读 RNG 预览、队列查看和带 `debug_intervention` 因果记录的调试排程。
- 当前自动测试为 19 项；构建、格式、场景校验、JSON、Markdown 链接和 NuGet 漏洞检查全部通过。

### 3.4 持久行动与旅行 `0.3`

- 已实现稳定 `ActionInstanceState`、行动序号、运行阶段、开始原因和旅行专用负载。
- 人物位置已严格区分“在地点”和“在路段”；中断时保存路线、方向和整数千分比进度，不回到起点或提前抵达。
- `Move` 已改为 `BeginTravel -> 路段事件 -> AdvanceAction` 的便捷包装；多路段旅行逐段调度并留下开始、完成和抵达因果。
- 已支持旅行中断、原方式或换方式恢复、取消，以及运行中或中断点保存/加载。
- 旅行风险使用 `travel-risk:action-id` 隔离随机流和整数阈值，事件记录抽取值、阈值、流键和结果。
- 同刻高优先级失能会立即改变行动状态并移除抵达事件，但玩家界面仍在同刻批次完整结算后暂停。
- 已证明目标人物可以在玩家旅行期间先离开；玩家抵达后交付失败，已付旅行时间不回滚。
- CLI 已能分别执行 `travel start`、`advance`、`actions`、`resume` 和 `cancel`，可在行动边界保存与加载。
- 当前自动测试为 41 项，覆盖运行中存档、中断存档、换步行恢复、取消、途中等待、共享时间轴、同刻冲突、自主 NPC、门禁和消息闭环。

### 3.5 运行时信念与自主 NPC `0.4`

- `BeliefState` 和 `PlanState` 已进入 `WorldState`，保存持有人、命题、置信度、来源事件、计划阶段、复评时间和关联行动。
- 王允的 `written_report_inspection.v1` 计划先等待正式报告；`Deliver` 完成普通物品转移后更新信念，并在同一分钟调度计划复评。
- 复评只读取计划所有者持有的信念与报告，不读取北门全局状态；满足条件后调用通用 `BeginTravel`，旅行完成再以 `plan_completed` 闭合因果链。
- 快照 schema 已升级为 `0.4`，保存文书元数据、信念、计划、挂起复评事件和关联行动。

### 3.6 访问、消息与认知 `0.5`

- 访问规则、人物组织身份、凭证适用范围和有效期、地点开闭状态已经进入运行时领域状态。
- `enter` 只允许请求相邻地点；非相邻请求不耗时，受限地点在五分钟通报后明确允许、拒绝或中断，并且拒绝结果不泄露内部人物状态。
- 普通旅行不能绕过门禁；同一分钟的权限变化先于抵达结算，已经付出的旅行时间不会因门禁收紧而回滚。
- 面对面陈述现在形成 `MessageState`，记录发送者、接收者、命题、置信度和上游消息；只有实际收到消息的人更新信念。
- 文书交付和口头消息在耗时期间都会处理世界事件；目标离开或玩家被中断时，不发生物品转移、消息送达或信念同步。
- 快照 schema 升级为 `0.5`，保存访问规则、人物身份、凭证、地点门禁状态和消息谱系。

### 3.7 精度与群体升降格 `0.6`

- 已将具名人物的 L0-L2 精度和 L3 聚合群体映射为纯领域状态；当前场景包含 15 个具名人物、7 个群体和 379 人口当量。
- 群体成员升格会原子减少群体人数，使用内容哈希、群体 ID 和单调序号派生稳定身份，不消耗普通随机流，也不会凭空增加人口。
- 临时人物只有在没有独立物品、承诺、计划、行动、消息、信念且回到来源群体位置时才能降格；否则明确拒绝，不静默丢弃因果。
- 快照 schema 升级为 `0.6`，保存群体、人物精度、升格来源、身份种子和升格序号；保存/加载后身份与人口游标保持一致。
- 已加入 B1 缩小版和 B4 结构子集入口：30 日空闲推进只处理 719 个实际事件；1,000 次升降格往返保持人口与物质状态指纹守恒。
- 该阶段完成时自动测试为 46 项；P6 的首批结果和未覆盖边界记录在[初始精度与规模报告](architecture/p6-scale-report.md)。

### 3.8 注意力与因果负债精度策略 `0.6.1`

- 已实现 `attention-and-causal-debt.v1`：玩家及同地人物为 L0，相邻人物、活动行动/计划、开放承诺和七日内消息参与者至少为 L1，其余具名人物可降为 L2。
- 每次精度变化产生 `actor_detail_level_changed`，记录策略版本、旧/新精度和判定理由；相同世界按稳定人物 ID 顺序重平衡得到相同事件指纹。
- CLI 新增 `dev rebalance-detail [person-id]`，可显式评估全世界或单个人物；当前重平衡仍由调用者触发，尚未接入每种世界状态变化后的增量失效队列。
- 已增加 B2 单城危机和 B3 消息扇出的缩小入口：12 名城内人物并发行动保持人口守恒；3 个命题经 14 名载体产生 42 条消息和 39 条父消息链接。
- 当前自动测试为 50 项；B1-B4 缩小结果及正式负载缺口记录在[初始精度与规模报告](architecture/p6-scale-report.md)。

## 4. 当前真实边界

当前内核已经证明“行动可以在运行中的世界里分阶段发生”，但还不能称为自行运行的世界，主要缺口是：

- 交付和陈述仍在一次同步调用中完成，尚未迁入统一持久行动协议。
- `state.json` 中的信念、人物计划、地点门禁与消息载体已进入运行时领域状态；群体传言升格和多计划协调仍未实现。
- 领域事件处理器目前覆盖旅行、访问变化、消息送达和测试用人物迁移；组织控制权与资源市场处理器仍未实现。
- 当前只有王允的一个通用规则计划会自行复评并通过与玩家相同的旅行规则改变世界。
- 访问和消息已经有首个闭环，但访问仍是同步五分钟尖峰，尚未拥有像旅行一样可单独保存于中途的持久行动实例。
- 骑马旅行已有风险与交通方式耗时，但马匹授权、实际持有转移、马料数量和伤病状态仍等待资源与访问规则。
- 已有确定性的注意力/因果负债精度评估和显式重平衡，但还没有由位置、行动、消息变化自动维护的增量脏集。
- 已有 B1-B4 缩小入口；B5、B6 以及目标规模下的正式 B1-B4 尚未实现。
- 还没有长期事件归档、增量快照、快照迁移器和事件日志分区。

因此，下一步不扩地图、不批量增加人物命令、不进入 Unity/Godot，也不先制作图形界面。

## 6. P3：持久行动与可中断旅行

本阶段已经完成。`Move` 不再直接跳转时间，玩家和未来 NPC 的旅行都表示为世界中的持久对象。

### 6.1 领域状态

- 新增稳定 `ActionInstanceState`，保存行动 ID、行动者、种类、状态、开始时间、当前阶段和直接原因。
- 新增旅行负载，保存起点、终点、路线、交通方式、当前路段、已行进分钟、已付成本和下一阶段事件。
- 明确位置表达：人物在地点或在某条路段上，二者互斥；中断时不得瞬移回起点或提前到终点。
- 行动状态至少支持 `scheduled`、`running`、`interrupted`、`completed` 和 `cancelled`。
- 快照保存运行中行动及其已付成本、队列事件和恢复所需游标。

### 6.2 引擎协议

- 将耗时命令拆为“验证并开始行动”和“推进到完成或中断”，避免一次调用隐藏全部中间状态。
- 旅行开始、路段完成、抵达和意外通过稳定事件种类处理器改变领域状态。
- 玩家与 NPC 使用同一旅行入口；CLI 只负责把同步交互包装在领域协议之外。
- 中断保留已经发生的时间、位置、物资和事件，不做命令级回滚。
- 支持从中断状态继续、改为步行或取消；每种选择留下新的原因边。

### 6.3 P3 验收

- 已用固定旅行风险流令骑马 40 分钟后发生马伤；人物和所持文书停在同一路段，40 分钟不回滚。
- 已验证旅行运行中和中断点保存；加载后继续与未重启运行具有相同状态、事件和随机流游标。
- 已排定早于抵达的人物离开事件；玩家到达后不能交付，物品和开放承诺保持原状。
- 已验证无效移动不推进时间、不创建事件，也不消耗行动或调度序号。
- 原有 54 分钟送信路径仍通过；消息显式化后共 11 个事件，直接单路段旅行继续只产生开始和完成两个核心事件。

## 7. P4：第一个自主 NPC 闭环（已完成）

本阶段已完成。只实现一个可解释的计划闭环，没有铺开完整 AI。

- 将场景中的运行时信念和计划映射进 `WorldState`，保留持有人、依据、阶段、复评时间和取消条件。
- 首选王允的城门报告计划作为低风险样例：等待报告、接收消息、更新信念、复评计划、产生检查或等待行动。
- 计划评估只读取人物可知状态，不读取全局真相；所有随机微扰使用人物决策专属流。
- 计划结果只能调用通用移动、访问、交付、陈述和等待规则，不能硬编码“历史必然发生”。
- 新消息、权限变化、资源不足或人物移除必须能够使计划暂停、替换或取消。

P4 的完成证据是一条可查询因果链：初始信念与计划 -> 复评触发 -> 行动选择 -> 分阶段行动 -> 状态变化 -> 新信念或后续计划。保存/加载和无关随机调用不能改变结果。

## 8. P5-P7 后续顺序

P5 已完成首个地点访问、门禁、消息载体和信念更新闭环。人物“知道什么”建立在真实接触和传播路径上，不会退化成全局变量同步。

P6 已完成前两步：L0-L3 状态与守恒升降格，以及由玩家距离、活跃计划、消息和未结因果驱动的确定性精度评估；B1-B4 均已有可运行缩小入口。下一步把全量显式重平衡改为状态变化驱动的增量脏集，再用 B5/B6 决定索引、分区、事件归档和增量快照方案。任何缩小负载都不得写成正式规模达标。

P7 才整合雒阳四日可玩 MVP：扩充只服务已经定义的访问、交付、跟踪、等待、消息和承诺用例。CLI 仍是首个正式客户端；只有领域端口稳定且核心验收通过后，才选择桌面或图形表现层。

## 9. 每个阶段的完成标准

任何阶段只有同时满足以下条件才算完成：

1. 通用领域规则中没有硬编码某个历史人物必须得到历史结果。
2. 新的耗时与状态变化由事件表达，重大结果有直接原因，可查询且可重放。
3. 相同场景、命令和随机状态重复运行得到相同事件与状态。
4. 快照保存全部新增可变状态；加载后续跑与不中断运行一致。
5. 无效输入不产生部分副作用；中断则保留已经真实发生的副作用。
6. 自动测试覆盖主路径、失败路径、同刻冲突和存档边界。
7. Release 构建零警告，格式、场景、JSON、Markdown 链接和漏洞检查通过。
8. 文档更新真实能力与剩余边界，必要的长期语义以 ADR 固定。

## 10. 计划维护规则

- 每完成一个阶段，更新“已经完成”“当前真实边界”和阶段状态，不只在提交记录中描述进展。
- 若验收暴露架构假设错误，先修订本计划与相应契约，再扩大实现范围。
- 新需求应归入已有阶段；若会改变多个模块的长期语义，先建立 ADR。
- 性能优化必须由规模基准驱动，不以牺牲确定性、因果或存档兼容为代价。
- 历史内容扩张必须继续经过研究主张和场景构建流程，不能直接硬编码进模拟规则。

# P6 精度与规模报告

> 状态：第四批架构验证，不是正式 B1-B6 达标报告<br>
> 日期：2026-07-24<br>
> 引擎：`0.6.2-spike`；快照 schema：`0.7`

## 1. 本轮验证的问题

P6 当前依次回答四个先决问题：L3 群体成员能否在不创造人口和随机人生的前提下成为可互动人物；空闲世界能否按到期事件推进，而不是按每分钟轮询全部人口；注意力变化能否只令相关人物精度失效；目标数量的人物移动和消息拓扑能否保持确定性、因果与守恒。它仍不声称已经模拟两百万人口的完整行为、100 万事件或 20 个长期分支。

实现使用四级精度：L0 近场人物、L1 同城或关键计划人物、L2 远方具名人物、L3 聚合群体。具名人物始终是独立领域对象；L3 只保存群体人数、位置、组织和升格 profile，不为每个人口当量创建对象。

## 2. 正确性契约

- 升格前验证来源群体非空，群体人数减一并创建一个稳定人物 ID，总人口不变。
- 身份种子由场景内容哈希、群体 ID 和单调升格序号经 SHA-256 派生，不消耗任何人物或世界随机流。
- 升格人物继承群体持有的信念，来源事件指向本次升格事件。
- 临时人物拥有独立物品、开放承诺、活动计划、行动、消息、独立信念或不同位置时，不允许降格。
- 干净降格删除仅由群体继承的临时信念，人物回并来源群体；事件日志保留升格和降格事实。
- 快照保存群体人数、精度、来源群体、身份种子和升格游标；加载后继续升格不会重用身份。

自动测试覆盖人口守恒、跨世界确定性、干净往返、消息阻止降格、快照续跑、注意力评估、活动行动保级、消息因果保级、局部空间失效、脏集快照和消息保留期到期。当前结果为 54/54 通过。

`attention-and-causal-debt.v1` 将玩家及同一注意空间的人物保持为 L0；相邻人物、活动行动/计划、开放承诺或七日内消息参与者至少保持为 L1；没有这些理由的具名人物可降为 L2。精度变化事件记录判定理由。

`0.6.2` 增加持久化增量脏集和派生空间索引。玩家从大将军府开始前往西市时，只标记玩家、原同地三人和相邻司隶校尉署的袁绍，共 5 人，而不是扫描或重评全部 15 名具名人物。刷新脏集后这些标记被原子清除。为了不破坏玩家动作的既有事件协议，刷新仍是显式边界；动作和世界事件只负责准确标脏。

目标规模负载由 benchmark 工程中的确定性工厂直接构造，不修改或伪造历史场景。B2 工厂创建 50 个 L0、500 个 L1 和一个 200 万人口当量的 L3 群体；B3 工厂创建 50 个地点和每地 4 名载体。每次样本都从全新世界开始，并以不变量和事件指纹拒绝不正确或不确定的快结果。

B1 的关键结果不是 10.59 ms 这个绝对值，而是 43,200 分钟的推进只结算 719 个到期事件。当前王允计划每 60 分钟复评一次，因此事件数并非零；调度器没有执行 `379 × 43,200` 次人物轮询。

B4 当前反复使用同一市场群体，升格后立即在没有独立互动的情况下回并。它证明稳定身份、事件记录、人口守恒和可审计降格成立，但尚未覆盖正式 B4 的随机群体选择、互动后保留、跨地点移动和批量资源核算。

B2 目标人口核心已经达到 50 个 L0 加 500 个 L1，并让除目标地点原有 10 人外的 540 人同时旅行。两次刷新严格只评估捕获的脏集，最终 550 人同地转为 L0；200 万 L3 人口当量始终是一个群体对象，总人口当量保持 2,000,550。当前 p95 `534.578 ms` 高于 B2 扩展架构预算 `< 250 ms`，分配中位数约 98.4 MB；因此结论是“正确但未达性能预算”，需要先分析 15,502 个旅行事件的追加、路径状态和精度评估分配，不能通过放宽预算掩盖。

这个 B2 负载只覆盖目标人口、并发移动和精度转换核心，尚未混合传信、访问、计划变更与远方世界低频运行，所以不能称为完整 B2。它的 12 小时推进只包含前 125 分钟的实际旅行结算和随后空闲推进；还没有实现“推进至多个玩家中断”的正式交互节奏。

B3 已达到 200 个载体和 50 个地点。玩家携带原始官方命题依次经过 50 个地点，每地形成“玩家 -> 载体 0 -> 载体 1 -> 载体 2 -> 载体 3”的四条真实消息；每地第一条是根消息，其余三条回指上游消息，因此总计 200 条消息和 150 条父链接。接收者信念逐一引用送达事件，没有批量写入认知。当前引擎尚未实现复述失真、竞争来源或冲突信念合成，所以这只是目标拓扑达成，不是完整 B3 语义达成。

B3 缩小版的计时与分配只包含消息传播；把 15 名人物聚集到西市的旅行准备发生在计时前，结束时世界分钟为 2264。工作集和最终事件指纹仍包含该准备阶段，因此报告没有把它伪装成零成本场景生成。B3 目标消息拓扑则把玩家沿 50 个地点的旅行计入模拟时间与分配。

## 5. 技术栈判断

当前没有证据支持更换 C#/.NET。核心仍只依赖 .NET BCL，场景、快照和 CLI 通过单向端口依赖核心；L3 没有展开为海量对象，事件推进也没有退化为全人口分钟轮询。未来若 SQLite、Godot、Unity 或 Web 客户端替换，领域规则和稳定快照 DTO 不需要随表现层重写。

这个判断是暂时的：B5 的百万事件追加与查询、B6 的分支隔离尚未验证，它们可能要求事件分区、只读基础快照、增量投影或数据库适配器，但不应先把数据库语义写进核心。

## 6. 下一步

1. 明确正式客户端和世界调度器消费脏集的稳定边界，避免精度维护事件改变玩家动作协议。
2. 分析 B2 的事件追加、旅行路径状态和精度评估分配，先让目标人口核心稳定满足 `< 250 ms`，再加入传信、访问、计划变更和玩家中断采样。
3. 为消息加入可版本化的转述失真、竞争来源与冲突信念规则，再把当前 B3 目标拓扑扩展成完整语义负载。
4. 用 B5 决定事件归档、投影和增量快照边界，再用 B6 验证 20 个分支的可变状态与随机流隔离。
5. 把每个正式样本隔离到独立进程，增加 GC 暂停和持续峰值工作集采样，并记录相对上一基准提交的变化。

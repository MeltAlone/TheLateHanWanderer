# 命令行 MVP 规格：雒阳四日

> 状态：可实现基线<br>
> 版本：0.1<br>
> 日期：2026-07-24

## 1. 要证明什么

首个可执行版本不是剧情试玩，也不是未来必须推倒的技术演示。它是最小的正式引擎切片，用四个游戏日证明以下闭环：

```text
人物依据有限认知形成计划
-> 在具体时空中执行有阶段、有耗时的行动
-> 行动产生不可变事件和客观状态变化
-> 目击、文书和传言改变人物认知
-> 新认知改变后续计划
-> 玩家可从自身视角观察、介入并追查结果
```

MVP 成功不以“复现何进之死”衡量。历史基线应由初始条件和通用规则自然产生；玩家或 NPC 改变关键条件后，结果可以偏离史实，但必须可解释、可回放。

## 2. 切片边界

| 项目 | MVP 决定 |
|---|---|
| 开始 | 中平六年八月丁卯辰时正；内部时间 `0` |
| 默认截止 | 中平六年八月辛未午后；内部时间 `6060` 分钟 |
| 核心空间 | 雒阳城、南北宫抽象节点、官署、市、城门与北郊 |
| 外围空间 | 孟津、小平津、夕阳亭、西来方向、成皋方向的抽象节点 |
| 玩家 | 虚构的低阶大将军府书吏，临时承担传递文书和口信的差遣 |
| 核心人物 | 何进、何太后、刘辩、刘协、袁绍、张让、王允、曹操、董卓、丁原、桥瑁等 |
| 模拟对象 | 重点人物、轻量具名人物、守卒/书吏/使者等群体单元 |
| 核心物资 | 文书、印信、凭证、钱、口粮、马匹与马料 |
| 暂不实现 | 战术战斗、全国经济、婚育继承、自然语言自由对话、图形界面 |

外围地点在 MVP 中用于真实占用时间和承载消息、军队、信使，不假装已经拥有完整城市内部模拟。

## 3. 玩家可知边界

命令行默认只输出角色能够感知或已经相信的内容：

- `look` 不列出藏在内室、城外或人群中的对象；
- `status` 不显示 NPC 的真实忠诚、计划分数或全局风险值；
- `ask` 和 `talk` 返回对方愿意表达的说法，不返回世界真相；
- 预计耗时是角色依据路线、天气和经验得到的区间，实际耗时可以不同；
- 失败文本只说明角色当时能够知道的直接原因；
- 远方变化只有经目击、信使、公告或传言抵达后才呈现。

开发者查询必须通过显式的 `dev` 模式运行，其输出不得进入玩家角色的信念、记忆或存档中的已知信息。

## 4. 命令协议

### 4.1 通用输入规则

- 命令使用稳定英文动词和实体 ID/无歧义别名；中文显示名不是持久化 ID。
- 输入在执行前完成解析和消歧。歧义命令不推进时间。
- 纯查询命令不推进时间；改变世界或进行观察的行动通常推进时间。
- 提交行动前显示预计耗时和明显成本；危险但角色未知的条件不泄露。
- `confirm` 只用于不可轻易撤销的行动，不是每条命令的固定步骤。

### 4.2 玩家命令

| 命令 | 语义 | 默认耗时 |
|---|---|---:|
| `look [target]` | 查看当前地点或一个已知目标 | 0；详细搜索转为 `observe` |
| `status` | 查看自身状态、身份、携带物和当前时间 | 0 |
| `go <place> [walk\|horse\|with-group]` | 沿可达路径移动 | 路径计算 |
| `enter <place>` | 请求进入相邻受限地点 | 5 分钟起，可等待或拒绝 |
| `talk <person>` | 发起一般交谈 | 15 分钟起 |
| `ask <person> about <topic>` | 针对一个已知主题询问 | 15 分钟起 |
| `observe <target>` | 花时间观察人物、地点或活动 | 15 分钟起 |
| `read <document>` | 阅读持有且有能力识读的文书 | 按篇幅，5 分钟起 |
| `give <item> to <person>` | 实际交付物品或文书 | 5 分钟起 |
| `tell <person> <proposition>` | 陈述一项主张，可真可假 | 5 分钟起 |
| `wait <duration\|time>` | 等待一段时间或到某时刻 | 指定时长，可中断 |
| `commitments` | 查看角色已知的约定、命令和期限 | 0 |
| `save <slot>` | 在稳定事件边界保存 | 0 游戏时间 |
| `load <slot>` | 加载兼容存档 | 不属于世界行动 |
| `help [command]` | 查看语法 | 0 |
| `quit` | 退出；有未保存进度时确认 | 0 |

第一版不提供 `attack`、`steal` 等未被切片验收覆盖的动词。玩家仍可能在事件中遭到拘捕或卷入冲突，但不能通过万能命令绕过尚未建模的规则。

### 4.3 开发者命令

```text
dev where <entity>
dev what-knows <person> [topic]
dev who-controls <place-or-resource>
dev why <event-or-state>
dev trace <entity-or-event>
dev history [entity]
dev plans <person-or-organization>
dev compare <save-a> <save-b>
dev audit-provenance [entity-or-field]
```

开发者命令只读。任何调试状态修改必须写成单独的外部干预事件，并使该回放标记为 `modified`。

## 5. 行动生命周期

每个耗时行动必须经过以下状态，而不是立即返回一个成功布尔值：

```text
proposed -> validated -> scheduled -> running
                         |             |
                         |             +-> interrupted -> resumed | cancelled
                         +-------------------------------> completed
```

行动结果至少区分：

- `completed`：预期阶段全部完成；
- `partially_completed`：已发生的阶段保留，后续阶段未完成；
- `refused`：目标明确拒绝，可能已经消耗通报和等待时间；
- `blocked`：客观前置条件不满足；
- `interrupted`：出现必须由玩家处理或使行动失效的事件；
- `cancelled`：行动者主动取消或计划撤销；
- `invalid`：语法、引用或静态命令条件错误，不推进时间。

例：送文书途中马匹受伤，骑行已经消耗的时间和马料不能回滚；玩家可改为步行、等待换马或取消差遣。若到达后对方拒收，路程同样已经发生。

## 6. 时间推进与同刻冲突

引擎只在玩家提交耗时行动或等待时推进。推进到下一个事件边界，处理事件后继续，直到行动结束、达到等待目标或出现玩家中断。

同一内部分钟的事件使用固定排序键：

```text
(due_time, phase_priority, stable_subject_id, event_sequence)
```

第一版 `phase_priority` 为：

1. `death_or_removal`
2. `access_and_control_change`
3. `arrival_and_departure`
4. `delivery_and_transfer`
5. `perception_and_belief`
6. `plan_evaluation`
7. `summary_and_notification`

排序只解决结算歧义，不代表叙事重要性，也不给玩家优先权。冲突的状态写入采用预定义规则，例如同一封文书只能由第一个有效转移事件取得，后续事件得到 `blocked:item_not_held`。

## 7. 随机、数值与回放

- 随机算法固定为 `xoshiro256ss.v1`；派生规则固定为 `sha256-le.v1`，见 ADR-0005。
- 随机流按领域和稳定实体 ID 派生，不允许使用语言运行时默认随机数。
- 时间、钱、物资、距离和概率阈值使用整数或定点数；核心状态禁止二进制浮点累计。
- 事件 ID、实体 ID 和排序不得依赖哈希表遍历顺序。
- 回放指纹由场景内容哈希、规则版本、随机算法版本、各流种子、玩家命令和外部干预共同决定。

保存点只能落在完整事件批次之后。运行中行动的状态必须显式保存，包括当前阶段、已付成本、下个中断点和已经排定的事件。

## 8. 场景和存档兼容

场景、规则和存档分别版本化：

| 标识 | 作用 |
|---|---|
| `schema_version` | 数据结构兼容性 |
| `scenario_version` | 内容修订版本 |
| `ruleset_version` | 行为语义版本 |
| `rng_version` | 随机序列实现 |
| `content_hash` | 实际加载内容的规范化哈希 |
| `engine_version` | 产生存档/日志的实现版本 |

加载策略：同一主版本直接加载；存在已登记迁移器时先迁移副本并保留原存档；规则语义不兼容且无迁移器时拒绝加载，并报告缺失版本。引擎不得静默采用新规则继续旧回放。

## 9. 内容错误必须显式失败

场景加载分两个阶段：先验证全部组件，再原子化创建世界。以下情况不得带病运行：

- ID 重复或引用不存在；
- 必填来源缺失或 `historical_claim` 指向未知主张；
- 路线端点、人物位置或物品持有者不存在；
- 计划目标永远不可解析；
- 时间窗倒置、资源为负或访问规则循环继承；
- 组件声明的场景、规则或 schema 版本不一致；
- 规范化内容哈希与清单不一致。

错误至少报告文件、JSON 路径、错误码和修复建议。一次验证应尽量返回所有独立错误，方便内容作者批量修正。

## 10. MVP 结束条件

只有同时满足以下条件，才进入更大地图或图形界面：

1. 验收规格中的玩家路径、无人干预基线和分叉路径全部通过。
2. 相同输入在重复运行、存档后续跑和事件回放中得到相同指纹。
3. 所有样例字段可审计到 `historical_claim`、`bounded_inference`、`gameplay_assumption` 或 `simulation_seed`。
4. 失约、拒绝、中断、取消和部分完成都留下可查询因果。
5. 远近精度切换不造成复制、瞬移、资源变化或既定计划遗失。
6. 未来规模基准达到 [世界规模预算](../../tests/performance/world-scale-budgets.md) 的阶段门槛。

通过这些门槛后再确定正式技术栈。当前优先候选是纯 C#/.NET 核心，但不能让 CLI、数据库或游戏引擎类型进入领域模型。
